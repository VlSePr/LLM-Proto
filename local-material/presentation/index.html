Two small changes, big stability win

RMSNorm & SwiGLU

RMSNorm

LayerNorm: (x − μ) / σ · g + b
RMSNorm: x / √(mean(x²) + ε) · g
  • No mean subtraction and no bias, so it's cheaper and just as stable
  • Pre-norm: applied before each sub-layer, so the residual stream stays raw
  • Computed in fp32 even under bf16 autocast

SwiGLU feed-forward

FFN(x) = Wdown( SiLU(Wgatex) ⊙ Wupx )
  • A learned gate decides, per dimension, how much signal passes
  • 3 matrices, so hidden = 8/3·d instead of 4·d keeps the parameters equal
  • 2048 → 5632 → 2048: 34.6M parameters per layer

Both come from the LLaMA paper lineage (Zhang & Sennrich 2019; Shazeer 2020). Neither is exotic; together they're the difference between a GPT-2 block and a LLaMA block.

Interactive · position as rotation

RoPE: rotary position embeddings

Each pair of q/k dimensions is rotated by an angle proportional to the token's position. After rotation, q·k depends only on the distance m − n, not on where the pair sits in the sequence.

query pos m key pos n dim pair i
Watch the dot product stay the same

Drag m and n: the relative angle changes. Then click "shift both": the two arrows spin, but the angle between them and the cosine stay fixed. That's the relative-position property.

Higher dim pairs (larger i) rotate more slowly, from 1 rad/token at i=0 down to ~1e-4 rad/token. Fast pairs encode local order and slow pairs long range. No learned parameters.

At inference, every generated token needs K and V for all previous tokens in all 32 layers: that's the KV cache. With MHA at 4k context and batch 8 it's 8 GB, more than the weights (3 GB in bf16).

GQA with 8 KV heads cuts it 4×. MQA goes all the way to 1 head but hurts quality. LLaMA-2-70B, Mistral and friends all use GQA.

Formula: 2 (K,V) × layers × kv_heads × head_dim × tokens × batch × 2 bytes.

Part 02

Data & tokenizer

A model is only as good as the tokens it sees, and you want to tokenize them exactly once.

src/data.py

Training never tokenizes

{ sources }

Sources

HF streaming, text dirs, JSONL. The base run used Project Gutenberg books.

BPE 32k

Tokenizer

Byte-level BPE with byte fallback: no unknown tokens, ever.

sha256(…)

Fingerprint

Tokenizer + source files + params. Change any of them and the data rebuilds.

uint16 .bin

Shards

100M-token binary shards + val.bin (every 200th doc) + manifest.json

Drive ☁

Cache

tokenized/<fingerprint>/ on Google Drive, so a new Colab VM downloads instead of re-tokenizing

uint16 is enough: vocab 32,000 < 65,536, so each token takes 2 bytes and gets memory-mapped straight into batches.
Cheap to check: the manifest + shard sizes are verified before any training step. A stale cache can't sneak in.
Colab-proof: VMs die. Tokenizing billions of tokens again costs hours; downloading shards takes minutes.

The core design rule: src.train only ever calls create_dataloader(data_dir). All the expensive, failure-prone work happens once, gets fingerprinted and is cached.

Pre-tokenized datasets from other sources can be pulled by folder (fetch_prebuilt_dataset). That path only checks the tokenizer hash.

src/tokenizer.py

What the model actually sees

“The United States Bill of Rights” is 6 tokens, not 32 characters. Ġ marks a leading space, so ĠUnited and United are different tokens.

<|bos|><|eos|><|pad|> <|im_start|><|im_end|>
  • 32k vocabulary trained on a 50k-document sample
  • Byte fallback: emoji, Cyrillic and code all encode, with no <unk>
  • ChatML markers reserved from day one, used later for chat
Per-token loss on the Bill of Rights. Dark red = surprise. “ĠTen”, “Pass”, “R|at|ified” are hard; “ĠStates” after “ĠUnited” and “Ġof” are nearly free. Loss is concentrated on the first token of new information.

Tokenization is where a lot of "LLM weirdness" comes from: counting letters, spacing, numbers split into odd chunks ("Ġ17" + "91"). Point at the heatmap. Once the model has committed to "United", "States" costs almost nothing.

Press → to walk through the seven stages; each one lights up its arrow. Clicking a numbered circle jumps to that stage.

  1. Code and the tokenizer come from GitHub (git clone in the notebook's first cell).
  2. Data is tokenized once (here on the workstation) and uploaded to Drive with a manifest and fingerprint.
  3. Colab mounts Drive and copies the shards to the VM's local disk; memory-mapped reads from Drive would be far too slow.
  4. Training on the GPU.
  5. Every 500 steps: an atomic checkpoint plus a Drive upload.
  6. When the VM dies, a new one clones, mounts, and resumes from latest.pt on the exact next batch.
  7. Inference: LLM-inference.ipynb loads a checkpoint from Drive and shares a Gradio link, which is the chat the audience has been using since the start.
src/train.py

The training loop

01

Optimizer

AdamW, β = (0.9, 0.95). Two param groups: no weight decay on norms, biases and 1-D params. Gradient clip 1.0.

02

Schedule

Linear warm-up, then cosine decay to min_lr (10% of peak). Warm-up keeps early, poorly-directed updates small.

03

Precision

precision: auto → bf16 on Ampere+ (and on our Blackwell), fp16 + GradScaler on older GPUs, fp32 on CPU.

04

Speed

torch.compile on CUDA (auto-off on Colab), flash SDPA, gradient accumulation. Gradient checkpointing must go in before compile.

for step in range(start_step, max_steps):          # start_step = ckpt["step"] + 1
    lr = get_lr(step, warmup, max_steps, peak_lr, min_lr)
    for micro in range(grad_accum):                 # 12 × 10 sequences per optimizer step
        loss = model(x, targets=y)["loss"] / grad_accum   # + aux_loss_coeff · aux_loss for MoE
        scaler.scale(loss).backward()
    clip_grad_norm_(params, 1.0); scaler.step(opt); opt.zero_grad(set_to_none=True)

Nothing here is novel. The point is that every piece is visible and testable: 6 seconds of CPU tests cover resume, OOM replay, schedules and MoE.

What's saved

Model, optimizer, GradScaler, all RNG states (Python / NumPy / torch / CUDA), epoch, batches_in_epoch, tokens seen, best val loss, both configs.

Deterministic data

Sample order is a pure function of (seed, epoch, worker layout). On resume, skip_batches fast-forwards the index stream without reading any data.

Safe on disk

Atomic write (tmp + os.replace), copy to latest.pt / best.pt, prune to N, then a best-effort upload to Drive.

A checkpoint's step is the last completed step, so resume starts at step+1. There's a test that trains N steps straight through, then N/2 + interrupt + resume, and asserts the two runs have identical weights.

Weights are saved without the _orig_mod. prefix that torch.compile adds.

Interactive · never lose a step to OOM

OOM? Replay the step, shorter

  • All micro-batches of a step are held, so the whole step can be retried
  • On OutOfMemoryError: free the cache and cut the sequence cap by 25%
  • Floor at min_seq_len (256). Below that it's a real bug, so it raises
  • The optimizer only steps once a full replay succeeds, so updates are never half-applied

Memory spikes are data-dependent (activation memory, allocator fragmentation). Instead of crashing at 3 a.m., the trainer shrinks the sequence cap: 4096 → 3072 → 2304 → …

Checkpoint sizes are arithmetic: fp32 weights (4 bytes/param) + AdamW's two moment buffers (8 bytes/param) ≈ 12 bytes × params. Inference only needs the bf16 weights (2 bytes/param).

Tokens/step and time/step use the current notebook settings (batch 12 × accumulation 10 × 4096 context). Earlier segments of the run may have used different settings, so treat the step time as indicative.

Data numbers come from the manifests: Gutenberg 5.50B train + 24.5M val tokens; the chat mix is 1,218,948 conversations, 980M tokens, 722M of them assistant tokens that carry loss.

Last 1,500 steps of the run

Is it still learning?

Train loss is noisy (1.75 – 2.32). Each point is one batch, and some text is simply easier. Don't read tea leaves in it.
Validation keeps falling: 1.911 → 1.881, perplexity 6.76 → 6.56, even at the tail of the cosine schedule.
Not converged. A still-sloping val curve at min LR means more tokens would help more than more steps.

The val curve is the only one to trust. The bump around step 23,650 is within eval noise (10 eval batches). The model is under-trained by Chinchilla standards (~20 tokens per parameter ≈ 30B tokens for 1.5B).

What a healthy run looks like

Training health

Learning rate: the cosine lands smoothly on min_lr = 6e-5 at step 24,000.
Gradient norm stays at ~0.2 with rare spikes to 0.43, well under the clip at 1.0. No instability.
Throughput is flat at 14,780 – 14,800 tok/s. The data loader is never the bottleneck.

These three are the first things I look at when a run misbehaves. A growing grad norm, or throughput that saw-tooths (loader starvation), shows up here long before the loss tells you.

Layer 0 · head 0

Where does it look?

  • Causal: the upper triangle is zero, so no peeking at the future
  • Attention sink: early tokens soak up a lot of attention. <|bos|> works as a “nothing to attend to” slot
  • Layer 0 is mostly a uniform average of the recent past. Sharp, content-specific heads live deeper
  • Faint vertical stripes on . and newlines: punctuation carries “where am I in the text” information

Attention sinks are a known phenomenon (Xiao et al. 2023, StreamingLLM). Softmax has to put probability somewhere, and the first token becomes the default dump.

32 layers deep

The residual stream grows

Activation std: 3 → 24. Every block adds to the stream, and pre-norm lets it grow without destabilising the next layer.
Late layers write louder: wo, wv and FFN weights grow with depth, while ffn_norm gains shrink to compensate.
Layer 0 is special: outlier wk and tiny attn_norm, since it works on raw embeddings.

This is the "health check" for a deep network: no dead layers (std ≈ 0), no explosions. The steady growth is expected with pre-norm residual architectures.

It speaks fluent 19th century

A base model doesn't answer questions. It continues documents. Ask it anything and it writes the next page of a Gutenberg book.

This is the most important conceptual slide of part 4. Pre-training gives you a document-continuation engine with the "voice" of its corpus. It has never seen a question followed by an answer, so it doesn't know that's what we want.

src/corpus.py · src/generate.py

Teaching it to take turns

<|im_start|>user
Is gravity a force?<|im_end|>
<|im_start|>assistant
In general relativity, gravity is not a force
but the curvature of spacetime…<|im_end|>   ← stop token

corpus.format_chat_pair wraps every instruction/answer row. The model learns where an answer ends.

  • Clean, then wrap. The corpus cleaner strips any <|…|> text, so it must run per field before the markers are added
  • Two stop ids: <|eos|> and <|im_end|>
  • Trim role leaks. If the model starts writing a fake “user” line, cut the reply there and never feed it back into history
  • Windowed repetition penalty (last 512 tokens), so long chats don't slowly ban the whole vocabulary

Supervised fine-tuning doesn't add much knowledge. It teaches format: who's speaking, when to stop, markdown lists, "Certainly!". Our chat outputs show exactly that. The form is right and the content is still 1.5B-parameter mush.

The point of this slide: none of these are mysterious "AI hallucinations". Each maps to a concrete mechanism we've seen in this talk: the tokenizer, sampling, the training data, the chat format, context.

The glued-words explanation is our best hypothesis. It shows up with repetition penalty ≥ 1.5 on long generations.

Bonus · src/moe.py

Next step: grafting experts

  • After pre-training: swap the FFN in layers 24–31 for a router + experts
  • Warm start: each expert begins as a copy of the dense FFN, so the output is unchanged at graft time
  • Freeze the rest, fine-tune on a domain (we used Dark Souls / Elden Ring lore), then grow one expert per round
  • Parameters grow with the number of experts, but compute per token stays at top-k FFNs: the Mixtral / DeepSeek idea

Only a mention today, about 1 minute. MoE is how Mixtral, DeepSeek and friends scale: parameters grow with the number of experts, but compute per token stays at top_k FFNs. We do it post-hoc: take the dense 1.5B, swap in SparseMoE in the last 8 layers, and fine-tune on a domain.

If you do this yourself

Lessons learned

01

Data is the model

Gutenberg in, Victorian out. Page markers, dialect and ALL CAPS all came from the corpus. Curate before you scale.

02

Plumbing > math

model.py is ~550 lines out of ~6,500. Resume, caching, OOM replay and Drive sync are the rest, and they're what saved the budget.

03

Decoding matters

The same weights produce poetry or glued gibberish depending on four sliders. Test sampling settings like code.

04

Format ≠ knowledge

Fine-tuning taught turns and markdown, not facts. At 1.5B parameters, fluency comes long before truth.

Build one once. You'll never read an LLM's output the same way again.

The fourth lesson is the one most relevant to people building products on LLMs: the polish of the output is not evidence of correctness.
